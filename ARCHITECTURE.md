# Mi Lumruri (mi-lumruri) для Xiaomi BE7000 со стоковой прошивкой 1.1.38

Целевая платформа — Xiaomi BE7000 (RC06), штатная прошивка 1.1.38. Документ описывает выбор компонентов, устройство выборочной маршрутизации и критерии испытаний. Описание соответствует версии 0.4.0. Проект называется Mi Lumruri, внутренние имена прежние: пакет `mi-lumruri-*.tar`, каталоги `/data/mi-lumruri` и `/tmp/mi-lumruri`.

Начиная с релизов 0.3.x комплект работает на физическом BE7000. Ставится он с компьютера через `install.py` или прямо на роутере через `tools/device/install-from-github.sh`. Найденные там особенности прошивки учтены в коде: BusyBox `sleep` не принимает дробные секунды, правила прошивки в mangle OUTPUT переписывают метку пакетов роутера. Первую из них теперь ловит CI: сценарии роутера проходят `sh -n`, `tools/lint-sh.py` (конструкции, которых нет в BusyBox стока) и `shellcheck -S error`. Прохождение приёмки по списку в конце документа пока не задокументировано.

## Решение для BE7000

Модель взята у [TrustTunnelOpenWrt](https://github.com/NooBiToo/TrustTunnelOpenWrt): выборочная маршрутизация по спискам доменов и IP, официальный клиент TrustTunnel, простая панель «сервер — сайты — устройства». Отличие в платформе: на стоке нет nftables и OpenWrt-пакетов, поэтому маршрут выбирают штатные iptables 1.6.2, ipset и dnsmasq.

Пользователь один раз передаёт подписанный пакет установщику по уже доступному SSH. После установки роутер сам поднимает службы при каждом включении. Код, настройки и сжатые программы хранятся во внутреннем постоянном разделе `/data`. Службы запускаются из `/tmp/mi-lumruri` в RAM. Холодный старт использует локальный пакет, сеть для запуска не нужна.

В официальном образе RC06 1.1.38 (ядро 5.4.164) есть модули `tun.ko`, `xt_set.ko`, `ip_set_hash_ip.ko`, `ip_set_hash_net.ko`, `xt_mac.ko`, `xt_mark.ko`, `xt_physdev.ko`, `xt_NFQUEUE.ko`, `xt_multiport.ko` и соответствующие расширения iptables. В конфигурации ядра включены `CONFIG_NETFILTER_NETLINK_QUEUE=y`, `CONFIG_BRIDGE_NETFILTER=y` и `CONFIG_IP_MULTIPLE_TABLES=y`. Штатный BusyBox 1.25.1 собран для AArch64 с musl. Перед каждым применением `mi-tt-admin caps` проверяет эти возможности на работающем ядре, включая сборку dnsmasq с ipset. Если чего-то нет, правила не меняются. SHA-256 исследованного образа — `77d8bd587418310c12c32922f8af63994079baa12c3a4772891494631bd84d8e`. [Образ Xiaomi RC06 1.1.38](https://cdn.cnbj1.fds.api.mi-img.com/xiaoqiang/rom/rc06/miwifi_rc06_firmware_65d1d_1.1.38.bin)

Особенность DNS на 1.1.38: запущенный dnsmasq читает `/tmp/dnsmasq.d`, а штатная инициализация копирует туда постоянные настройки из `/etc/dnsmasq.d`. Служба кладёт свой файл в `/tmp/dnsmasq.d/mitt.conf` и перезапускает dnsmasq только при изменении файла. [Диагностика Enodia](https://github.com/Axel173/enodia/blob/5e06ff01295b7cb044bd26249a2c9b52a56cbf9b/dump.sh#L737-L750)

Из исходников [Enodia](https://github.com/Axel173/enodia/tree/5e06ff01295b7cb044bd26249a2c9b52a56cbf9b) (GPL-3.0, код не заимствуется) учтены два наблюдения:

- Пустая таблица VPN-маршрутов допускает выход через основную таблицу. Поэтому в таблице 3100 при отказе туннеля стоит `unreachable`, если в профиле не выбран обход. [mark-core.sh](https://github.com/Axel173/enodia/blob/5e06ff01295b7cb044bd26249a2c9b52a56cbf9b/mark-core.sh#L1-L22)
- При изменении настроек радио прошивка может переназначить имена интерфейсов. Сеть хранится как логическая сущность с мостом и портами, порты задаются в панели. [wifi-lib.sh](https://github.com/Axel173/enodia/blob/5e06ff01295b7cb044bd26249a2c9b52a56cbf9b/wifi-lib.sh#L1-L38)

## Сетевые компоненты

| Компонент | Реализация | Что проверить на роутере |
|---|---|---|
| Туннель | `trusttunnel_client -c client.toml`. Конфигурацию формирует `mi-tt-ctl render`: TUN `mitt0`, MTU 1350, пустые `included_routes`, `change_system_dns = false`, `upstream_protocol` `http2` или `http3`, `anti_dpi`, `tls_profile` (по умолчанию `chrome`; также `chrome_canary`, `safari`, `firefox`, `okhttp`, `openssl`, `boringssl`), `client_random` или `client_random_auth_key`. Сервер задаётся IP или доменом, домен клиент разрешает сам. За доменом в `addresses` идут до трёх запасных IP из `etc/server-addrs` (их служба запоминает после удачных подключений, `fallback_addrs` в `render.rs`), поэтому без DNS на старте клиент подключается по IP. `has_ipv6 = true`, если включено «IPv6 через VPN» и есть источники «всё через VPN». При заданном запасном сервере рендер пишет ещё `client-backup.toml` и `primary.addr`. Клиент только поднимает TUN; что в него направить, решает `mi-tt-admin` | Соединение с реальным сервером, HTTP/2 и HTTP/3, восстановление после потери WAN, нагрузка на CPU |
| Выбор маршрута | Цепочки `MITT_*` в mangle PREROUTING ставят бит `0x4000` (при нескольких серверах — и номер туннеля в поле `0xf0` или `0x0f00`); `ip rule fwmark … lookup 3100+n`; в таблице 3100+n `default dev mitt<n>` | Прохождение с включённым аппаратным ускорением NSS/ECM, отсутствие конфликтов меток с прошивкой |
| Домены | dnsmasq заносит адреса ответов в ipset `hash:ip` (`ipset=/домен/набор`, срок записи — сутки). Домены правил туннеля разрешаются через резолвер туннеля, по желанию — по DoH/DoT поверх туннеля | Наличие ipset в штатном dnsmasq, перезапуск штатной службой, порядок старта |
| Шифрованный DNS | `mi-tt-dns`: DoH (HTTP/1.1, keep-alive) или DoT в постоянных соединениях, сервер задан IP-адресами. Экземпляр на `127.0.0.1:5453` — для остальных доменов, запасной путь к DNS провайдера. Экземпляр на `127.0.0.1:5454` — для доменов туннеля, сокеты привязаны к `mitt0`, запасного пути нет | Ответы после холодной загрузки с неверными часами, работа через туннель |
| Zapret | NFQUEUE (очередь 200, `--queue-bypass`) в mangle FORWARD: первые пакеты соединений к портам профилей (TCP — 25, UDP — 5 по connbytes), обработчик nfqws2 с профилями каталога. Подбор стратегии — очередь 201 в mangle OUTPUT для TCP роутера с портов 61000–61099 | Прохождение пакетов через очередь по кабелю и Wi-Fi при включённом ускорении, подбор против DPI провайдера |
| Блокировка | REJECT в filter FORWARD | — |
| Реклама | `address=/домен/` в файле dnsmasq: NXDOMAIN, вопрос наружу не уходит. Список скачивает служба (HaGeZi Light, HaGeZi Normal или своя ссылка), проверяет `mi-tt-ctl adblock-check`, хранит копию в RAM и сжатую в `/data`. Исключения | Контрольные разрешённый и заблокированный домены |
| Свои записи | `address=/домен/адрес` в файле dnsmasq: домен с поддоменами отвечает заданным IPv4 или IPv6, не больше 256 записей | Ответ для домена и поддомена |
| Панель | HTTPS в LAN на 8443, вход паролем, по желанию TOTP | Вход после холодной загрузки без точного времени |

### Бюджет хранения и оперативной памяти

Размеры из отчёта последней локальной сборки `out/package/report-<версия>.json` (`node tools/package.mjs`). У сборки CI другие строка версии (`ci-<коммит>`) и ключ подписи, поэтому размеры TAR и манифеста у неё немного другие. Программы сжаты XZ (preset 6, словарь 8 МиБ, CRC32) и распаковываются штатным BusyBox `unxz` при загрузке. Три программы контроллера с версии 0.4 собраны в одну, `mi-tt`: общий код (serde, TLS, SHA-256, стандартная библиотека) хранится один раз. Распаковка создаёт ссылки `mi-tt-ctl`, `mi-tt-admin` и `mi-tt-dns`, программа выбирает, что выполнять, по имени ссылки. Это экономит 484 КБ в пакете и 1,2 МБ в RAM. Более сильное сжатие (`-9e`) не даёт выигрыша, а фильтр ARM64 BCJ BusyBox 1.25 не распаковывает.

| Файл | В пакете, байт | В RAM после распаковки, байт |
|---|---:|---:|
| `trusttunnel_client` v1.3.0 | 2 808 776 | 8 624 304 |
| `mi-tt` (`mi-tt-ctl`, `mi-tt-admin` и `mi-tt-dns` в одной программе) | 951 704 | 2 269 240 |
| nfqws2 (zapret2 v1.0.7) | 317 336 | 318 196 |
| Панель, сценарии, Lua, блобы и списки хостов zapret2, снимок списков сайтов, настройки, NOTICE | около 417 000 | около 1 036 000 |
| **Всего** | **TAR 4 608 000; в `/data` 4 495 286** | **12 247 530** |

`/data` на BE7000 — около 20,6 МБ, из них около 9 МБ занимает прошивка. Установщик требует свободными в `/data` объём релиза плюс 2 МиБ резерва, в `/tmp` — объём распаковки плюс 16 МиБ на работу процессов. Релизы лежат в `releases/` хранилища (по умолчанию `/data/mi-lumruri`); после установки остаются только текущий и предыдущий, остальные удаляются. Если места не хватает, установщик сначала удаляет все релизы, кроме текущего. Если и после этого свободно меньше нужного, но не меньше объёма релиза плюс 512 КиБ, установка идёт впритык: прежний релиз удаляется после переключения, откат на него недоступен, настройки сохраняются. Меньше — отказ с предложением хранить релизы на USB-накопителе (`--store`). Прежний комплект на Mihomo и dnscrypt-proxy занимал 18,4 МБ в пакете и около 72 МБ в RAM.

### Установка, запуск и обновление

1. Установщик проверяет модель, архитектуру ARM64, место в `/data` и `/tmp`, возможность исполнять файлы в `/tmp`, наличие `unxz`. До изменений проверяет подпись манифеста (Ed25519) и хэши, распаковывает файлы в RAM, сверяет их и пробно запускает все программы (`mi-tt-ctl`, `mi-tt-admin`, `mi-tt-dns`, `trusttunnel_client`, nfqws2). При первой установке открытый ключ из манифеста закрепляется в `/data/mi-lumruri/keys/release.pub`. Обновление проверяется уже установленным `mi-tt-admin` по закреплённому ключу. Пакет с другим ключом отклоняется, установщик печатает оба отпечатка (`mi-tt-admin release key-fingerprint`). Смена ключа — только явная: `install.sh install --trust-key=<16 hex>` (`install.py --trust-key`) принимает пакет, если его отпечаток совпал, и закрепляет новый ключ после переключения `current.ver`.
2. Релиз копируется в `<хранилище>/releases/<версия>.tmp`, затем переименовывается. Указатели `current.ver` и `previous.ver` заменяются атомарно. Автозапуск — `uci firewall.mitt` (include типа script) на постоянную точку входа `/data/mi-lumruri/mitt-boot.sh`.
3. При загрузке и каждой перезагрузке firewall fw3 вызывает `mitt-boot.sh`. Холодный старт: распаковка в RAM со сверкой по манифесту, синхронизация списков, `render`, `apply --guard-only` (трафик правил туннеля закрыт до запуска клиента), панель, служба. Если служба уже работает, `mitt-boot.sh` только восстанавливает свои правила (`apply`).
4. Служба (`mitt-service.sh`) запускает движки по порядку. Первым — `mi-tt-dns` на 5453: служба ждёт, пока он ответит на пробный вопрос (`--probe`, до 10 попыток по 0,2 с), потому что dnsmasq, а через него и клиент TrustTunnel, разрешающий имя сервера, уже спрашивают этот прокси. Затем `mi-tt-dns` на 5454 для доменов туннеля, если включено шифрование DNS через VPN. Затем клиент TrustTunnel: служба ждёт до 15 с, пока `mitt0` поднят и получил IPv4-адрес, потому что маршрут таблицы 3100 ссылается на него. Последним — nfqws2. Паузы по 0,2 с делает `usleep`: `sleep` штатного BusyBox не принимает дробные секунды. Перед перезапуском движков служба ждёт, пока ядро удалит прежний `mitt0`.
5. После запуска движков служба применяет полную политику, затем синхронизирует файл dnsmasq (наборы ipset к этому моменту созданы). Если полное применение не прошло, действует защита (`--guard-only`); когда `mitt0` готов, служба повторяет применение не чаще раза в минуту. Вывод неудачного применения сохраняется в `run/apply.<метка>.fail.json`, время перезапусков упавших движков — в `run/restarts` (последние 50).
6. Служба выполняет заявки панели (применение, перезапуск, диагностика, подбор Zapret, обновление списков, подписка, обновление пакета), по расписанию проверяет обновления списков сайтов, списка рекламы и подписки, запускает автопроверку Zapret и перезапускает упавший движок.
7. На каждом проходе, пока клиент TrustTunnel запущен, служба вызывает функции `mitt-lib.sh`:
   - `server_addr_learn` — берёт из журнала клиента строку `Using endpoint: name=…, address=…` и записывает IP в `etc/server-addrs` (до трёх, свежий первым; файл переписывается, только если адрес новый);
   - `tunnel_watch` — раз в минуту, если клиент в состоянии `VPN_SS_CONNECTED` и `mitt0` готов, делает `curl --interface mitt0` к `https://1.1.1.1/cdn-cgi/trace`, при неудаче — к `https://8.8.8.8/`. Три неудачи подряд — остановка клиента (цикл службы запустит его заново), не чаще раза в 5 минут. Итог — `watch.json`, его читает диагностика (строка «Сторож туннеля»);
   - `failover_check` — если есть `client-backup.toml`: клиент не в `VPN_SS_CONNECTED` дольше 2 минут — переключение на другой сервер (состояние `endpoint`: `primary` или `backup`; оба недоступны — по очереди). На запасном раз в 5 минут проверка основного по `primary.addr`: `curl` к `https://адрес:порт/`, любой ответ или ошибка TLS — порт открыт, коды 6, 7 и 28 — нет. Две удачные проверки подряд — возврат. Смена — остановка клиента, цикл службы запускает его с нужным файлом. Текущий сервер служба отдаёт в `status.json` (`endpoint`).
8. Без WAN панель доступна, трафик правил туннеля заблокирован. Когда WAN появляется, клиент подключается сам.
9. Раз в минуту служба отдаёт `/proc/mounts` и вывод `df -k` команде `mi-tt-ctl storage-scan` (`storage_scan` в `mitt-lib.sh`). Итог — `run/storage.json`: внутренняя память пакета и USB-накопители (`/dev/sd*` под `/mnt/` и `/extdisks/`) с местом, файловой системой, флагами `ro`/`noexec` и производителем и моделью из sysfs. Панель читает его через `GET /storage` (страница «Модули»).
10. **Модули.** Модуль — отдельный tar (`mitt-mod-<имя>-<версия>.tar`, ассет релиза) с каталогом `module/`: манифест того же формата, что у пакета, подпись Ed25519 тем же ключом и `payload/*.xz`. Каталог модулей (`payload/scripts/modules.json`: версия, имя ассета, SHA-256 и размеры tar, виды профилей) входит в подписанный пакет; служба кладёт копию в `run/modules-catalog.json`. Установка (`mitt-module.sh` по заявке `POST /modules/install`): загрузка с GitHub (`releases/latest/download/<ассет>`, затем поиск по списку релизов), сверка SHA-256 с каталогом, распаковка `tar` на накопитель (`<точка монтирования>/mi-lumruri-modules/<имя>` или `/data/mi-lumruri/modules/<имя>`), `mi-tt-admin release verify --pinned`, запись в `etc/modules.json`. При старте службы `modules_prepare` распаковывает установленные модули в RAM (`/tmp/mi-lumruri/mod/<имя>/`, сверка распакованного с манифестом); дальше программа модуля не читает накопитель. `modules_watch` раз в 30 с проверяет накопитель: пропал — уведомление `module_missing` (или `module_missing_off`, если в RAM программы нет), вернулся — `module_back`, распаковка и применение. sing-box для модуля — статическая сборка `linux-arm64-musl` (сборка `linux-arm64` требует glibc, на стоке musl).
11. **Серверы модуля sing-box** (виды vless, hysteria2, trojan, shadowsocks): в настройках — сводка `Profile.proxy`, сервер — ссылка `secrets.profiles[id].link` (`controller/src/proxy.rs` разбирает её и строит выход sing-box). Рендер пишет `tun<n>/sing-box.json`: вход TUN `mitt<n>` с `auto_route: false` и стеком `system` (маршруты и метки — mi-tt-admin), один выход, имя сервера — через системный DNS роутера. Служба запускает `sing-box run -c` на каждый такой туннель (процесс `singbox<n>`); «подключён» — процесс жив, сторож проверяет трафик через TUN, как у TrustTunnel. В `tunnels.list` четвёртое поле — программа туннеля.

## Как выбирается маршрут

Правило содержит источник, назначение и действие.

- **Источник:** устройство (MAC на входе моста), сеть (мост целиком или порты моста — интерфейсы SSID — через physdev), вся LAN (мост).
- **Назначение:** точный домен, доменный суффикс, IPv4-подсеть, группа назначений, категория (локальный список доменов или IP-префиксов).
- **Действие:** через TrustTunnel, напрямую, напрямую с Zapret, блокировать.

Правила применяются по уровням: устройства, затем сети, затем вся LAN. Внутри уровня — в порядке, заданном пользователем, побеждает первое совпадение. Остальной трафик LAN получает действие по умолчанию.

Как это выражается на стоке (подробно — в заголовке `controller/src/plan.rs`):

1. Назначения превращаются в наборы ipset. Адреса доменов заносит dnsmasq в набор `hash:ip`, IP-префиксы и IP-категории лежат в статическом наборе `hash:net`.
2. В mangle PREROUTING цепочка классификации проверяет правила по порядку. Для действия «через TrustTunnel» она ставит бит `0x4000` — единственный свободный бит метки на стоке (остальные заняты QoS, mwan3, родительским контролем). Пакет с битом уходит по `ip rule` приоритета 3005 в таблицу 3100, где стоит `default dev mitt0`. Пока туннеля нет, в таблице действует `unreachable`, если в профиле не выбрано «пускать напрямую». Трафик внутри LAN исключён правилом приоритета 3000 (`to <подсеть> lookup main`).

   **Несколько серверов.** У каждого профиля постоянный номер туннеля n (0–15, `Profile.tunnel`): свой клиент TrustTunnel, TUN `mitt<n>`, таблица 3100+n и правило приоритета 3005+n. Пока используется один туннель, план не отличается от одиночного (`0x4000/0x4000`; у туннеля n≠0 — его таблица). При двух и больше номер записывается в поле метки рядом с `0x4000`: основное — `0xf0` (резерв плагина UU в `miqosd_init.sh`), запасное — `0x0f00` (половина резерва mwan3). Метка туннеля n — `0x4000 | n<<4` с маской `0x40f0` (или `n<<8` и `0x4f00`). Поле выбирает mi-tt-admin при каждом применении по живому состоянию (`choose_field`): правила iptables вне цепочек `MITT_*` и `ip rule` вне зоны 3000–3199, задевающие поле, делают его занятым. Оба поля заняты — план сужается до туннеля с наименьшим номером (`degrade`): правила остальных — REJECT (политика «блокировать») или без метки («напрямую»). Выбранное поле и признак сужения — в состоянии mi-tt-admin (`mark_field`, `degraded`). DNS-вопросы роутера к резолверу туннеля идут в туннель `dns.tunnel_profile` (по умолчанию — с наименьшим номером), IPv6 через VPN — в туннель сервера по умолчанию. При нескольких туннелях `mi-tt-dns` для доменов туннеля держится только привязкой к TUN, без `SO_MARK`: номер в метке знает лишь mi-tt-admin.

   Рендер пишет файлы туннеля 0 по прежним путям каталога рендера, туннеля n>0 — в `tun<n>/`, а список «номер TUN профиль» — в `tunnels.list`; служба (`tun_ctx` в `mitt-lib.sh`) запускает клиент, сторож, запасной сервер и уведомления на каждый туннель (`trusttunnel<n>`, состояние в `$STATE/tun<n>/`).
3. В filter FORWARD та же классификация: «блокировать» — REJECT. Выход в `mitt0` разрешён явно, потому что fw3 стока отклоняет пересылку на интерфейс вне зон.
4. В mangle FORWARD для «напрямую с Zapret» первые пакеты соединений к портам профилей (TCP 80 и 443, UDP 443 для QUIC, порты голоса Discord) уходят в NFQUEUE 200 для nfqws2. Пакеты, которые генерирует nfqws2, помечены `0x40000000` и повторно в очередь не попадают. Цепочка в mangle OUTPUT отправляет в очередь 201 проверочные запросы подбора стратегии.
5. Домены правил туннеля dnsmasq разрешает через резолвер туннеля (`server=/домен/IP`, по умолчанию 1.1.1.1, настройка `dns.tunnel_resolver`). DNS-запросы самого роутера к этому резолверу помечаются в mangle OUTPUT и идут в туннель: провайдер не видит и не подменяет ответ. Если включено шифрование через VPN (`dns.tunnel_secure`, только Cloudflare, Google, AdGuard и Quad9 по DoT), dnsmasq спрашивает `127.0.0.1#5454`, а `mi-tt-dns` ходит к резолверу по DoH или DoT. Его сокеты привязаны к `mitt0` (`SO_BINDTODEVICE`, `--device mitt0`) и несут метку `0x4000` (`SO_MARK`). Одной метки мало: правила прошивки в mangle OUTPUT переписывают её, пакет перемаршрутизируется мимо туннеля, и соединение получает `EHOSTUNREACH`. Запасного пути у этого экземпляра нет: без туннеля вопрос провайдеру не уходит.
6. Остальные домены при включённом защищённом DNS (`dns.secure`) dnsmasq отправляет только в `mi-tt-dns` на 5453 (`no-resolv`, `server=127.0.0.1#5453`). Если сервер DoH/DoT недоступен или сертификат не проходит проверку (например, часы после загрузки ещё неверные), прокси передаёт вопрос DNS провайдера из resolv-файла штатного dnsmasq. Адреса сервера прокси перебирает так: IPv4 по кругу, IPv6 — только если не ответил ни один IPv4. Свои записи (`address=/домен/адрес`) и домены туннеля точнее общего правила и действуют независимо от него.
7. У источников с правилами туннеля, Zapret или блокировки IPv6 наружу отклоняется: домены сопоставляются только по IPv4 (dnsmasq заносит в наборы только адреса IPv4). Исключение — «IPv6 через VPN» (`ipv6_via_vpn`) для источников, у которых правило туннеля покрывает весь IPv4 (`0.0.0.0/0` или `0.0.0.0/1` и `128.0.0.0/1`). Клиент поднимает IPv6 в туннеле (`has_ipv6`), цепочка в mangle ip6tables ставит бит `0x4000` всему IPv6 источника, кроме LAN-префиксов, `fe80::/10` и `ff00::/8`, а `ip -6 rule` отправляет его в таблицу 3100: маршрут через `mitt0`, при отказе туннеля — `unreachable`, если не выбран обход. Исключения и Zapret такого источника по IPv6 тоже уходят в туннель: правила по сайтам для IPv6 не строятся.

Цепочки называются по хэшу содержимого. Изменение применяется так: создаётся новая цепочка, переход переключается на неё, затем прежняя снимается. Зона владения: приоритеты `ip rule` и `ip -6 rule` 3000–3199, таблицы 3100–3115 (IPv4 и IPv6), цепочки `MITT_*`, наборы `mitt*`, бит `0x4000` и, при нескольких серверах, поле номера туннеля. Если в этой зоне есть чужие записи или правила прошивки используют бит `0x4000` (например, sticky-правила mwan3 с маской `0xfc00`), применение отклоняется без изменений.

Полная перезагрузка firewall снимает все цепочки iptables. До повторного вызова include трафик правил идёт напрямую. В лаборатории это окно составило 1,2 с.

## Простая панель, списки и Zapret

Панель не показывает модель правил: ответы на экранах «Сервер», «Сайты» и «Устройства» превращаются в конфигурацию канонического вида (`panel/src/simple.ts`):

- отмеченные сервисы — категории `svc-<id>` (домены) и `svc-<id>-ip` (подсети IPv4); группы `vpn-sites` (категории и свои домены), `zapret-sites` (сайты с обходом блокировок), `vpn-except` (исключения) и `vpn-all` (весь IPv4: `0.0.0.0/1` и `128.0.0.0/1`);
- сеть `home` — мост и подсеть LAN роутера из `network.lan` (API `/router`);
- для каждого источника (вся LAN или выбранное устройство) по порядку: `except-<src>` → «остальные сайты», `zapret-<src>` → напрямую с Zapret, затем `vpn-<src>`: `vpn-sites` (режим «Только выбранные») или `vpn-all` (режим «Всё через VPN») → профиль; `default_action` — профиль в режиме «Всё» для всей сети, иначе «остальные сайты» (напрямую или напрямую с Zapret);
- устройства «Весь интернет» (только в режиме «Только выбранные»): перед правилами источников — `except-<dev>`, `zapret-<dev>` и `vpnall-<dev>` → `vpn-all` → профиль;
- «Выключить VPN» — все правила `enabled: false`, `default_action` напрямую, выбор сохраняется.

Конфигурацию другого вида (правка через CLI) панель молча не переписывает, а предлагает привести к простому виду.

**Расписание.** Раздел `schedule` конфигурации: `lists` — проверка обновлений списков (`6h`, `daily` по умолчанию, `weekly`, `manual`) и `zapret_check` — автопроверка Zapret (`off` по умолчанию, `daily`, `weekly`). Рендер записывает периоды в секундах в файл `schedule` для службы.

**Списки сайтов.** `tools/fetch-lists.sh` кладёт в пакет снимок itdoginfo (Services, Categories, `Russia/inside-raw`, Subnets/IPv4) с каталогом `catalog.json`, закреплённый по коммиту (хэши файлов — в подписанном манифесте пакета). Перед каждым рендером `mitt-lists.sh sync` раскладывает файлы в `etc/categories/svc-*.list`: обновлённый файл из `/data/mi-lumruri/lists`, иначе файл из снимка релиза. `mitt-lists.sh update` (по расписанию и по заявке панели) скачивает файлы с `raw.githubusercontent.com` через curl стока, проверяет каждый командой `mi-tt-ctl category-check` и отбрасывает ответ, в котором меньше половины записей действующего списка. Изменения заменяются в `/data` атомарно, затем выполняются sync и заявка на применение. Без связи повтор — через час. Обновления привязаны к коммиту снимка: после установки релиза с другим снимком они не используются до следующей проверки.

**Реклама.** `mitt-adblock.sh` скачивает список по ссылке из настроек: HaGeZi Light (по умолчанию), HaGeZi Normal (`wildcard/light-onlydomains.txt` и `wildcard/multi-onlydomains.txt`) или свою ссылку `https://…`, не больше 12 МиБ. Список проверяет `mi-tt-ctl adblock-check`: HTML, пустой список или много мусора — отказ, единичные кривые строки пропускаются. Рабочая копия лежит в RAM, сжатая — в `/data`, поэтому после перезагрузки блокировка действует сразу. Загрузка идёт после каждой загрузки роутера, по расписанию списков, по кнопке «Обновить» и при смене ссылки. Новый список применяется заявкой.

**Zapret.** Каталог стратегий (`controller/src/zapret.rs`; наборы из [Zapret-Manager](https://github.com/StressOzz/Zapret-Manager), Apache-2.0, авторство указано в NOTICE) задаёт профили nfqws2 с фильтрами портов и списков хостов: общий, YouTube, YouTube по QUIC, Discord (TLS и голос по UDP). Режим «Автоматически» — круговой перебор zapret2 (`circular`, смена стратегии после 3 неудач). Lua-библиотеки, fake-файлы и списки хостов лежат рядом с nfqws2 в RAM (`--chdir`). Подбор (`mitt-zapret-test.sh`) использует отдельный nfqws2 на очереди 201 и проверочные запросы curl с портов 61000–61099, цели — в `zapret-targets.txt`. Сначала проверяется контроль без Zapret, затем каждая стратегия. Лучшая применяется, только если открыла больше контроля, и затем перепроверяется. Метка отката `etc/zapret-test.rollback` позволяет вернуть прежний выбор, даже если сценарий убит. Автопроверка по расписанию запускает тот же подбор, если Zapret используется и роутер работает больше 10 минут; новая стратегия применяется, только если она лучше действующей.

**Диагностика.** По заявке панели (`POST /diag`, по желанию с доменом сайта) служба запускает в фоне `mitt-diag.sh`. Сценарий только читает состояние и делает пробные запросы: служба, клиент TrustTunnel, внешний адрес, правила firewall, DNS и защищённый DNS (в том числе через VPN), Zapret, движки, перезапускающиеся по кругу за последние 10 минут, маршрут проверяемого сайта. Итог и хвосты журналов он кладёт в `run/diag`, контроллер отдаёт их по `GET /diag`. Кнопка перезапуска службы ставит заявку `restart.request` (`POST /service/restart`). Строка клиента показывает версию `trusttunnel_client` и время на связи с последнего `VPN_SS_CONNECTED`, строка «Сторож туннеля» — итог `watch.json`.

**Подписка.** Ссылка TrustTunnel 1.3 с тегом `0x0E` (раздел `[subscription]` сервера) хранится как секрет профиля. `mitt-sub.sh` скачивает по ней JSON, `mi-tt-ctl subscription-import` (`controller/src/subscription.rs`) переносит в профиль и `secrets.json` адрес, имя сервера, логин, пароль, HTTP/3, anti-DPI, сертификат и префикс client_random. Неизвестные поля пропускаются. Если что-то изменилось — заявка на применение. Запуск — по расписанию списков сайтов и по кнопке (`POST /subscription/update`), итог — `GET /subscription`. Ссылка, в которой есть только подписка, тоже принимается: остальное приходит после первой загрузки.

**Запасной сервер.** `profile.backup` — второй `Endpoint` того же профиля, пароль — `backup_password` в `secrets.json`. Профиль, метка и правила общие, меняется только файл клиента: `tt_config` отдаёт клиенту `client.toml` или `client-backup.toml` по состоянию `endpoint`. Переключение и возврат — `failover_check`, см. «Установка, запуск и обновление».

**Обновление из панели.** `GET /update` отдаёт итог, `POST /update` ставит заявку: `check`, `install` или `install` с `trust_official`. `mitt-update.sh` запрашивает последний релиз через API GitHub, скачивает TAR и `SHA256SUMS`, сверяет SHA-256 и запускает `install.sh` из пакета: подпись проверяется закреплённым ключом. Если ключи не совпали, панель предлагает перейти на релизы GitHub. Тогда `install.sh` получает `--trust-key` только с отпечатком ключа релизов `e4a271890e5643ab`, другой ключ так не принять. После установки служба перезапускается отдельным процессом.

**Лаборатория.** `tools/lab/run-lab-boot.sh` проверяет это на настоящем ядре: mi-tt-admin применяет цепочки Q, Z и P, и они совпадают с планом; nfqws2 x86_64 той же версии работает с отрендеренными аргументами каталога; трафик LAN проходит через очередь 200. По кнопке «Обновить списки» изменённый список загружается с локального «репозитория» и применяется заново. По кнопке «Подобрать способ» все стратегии проверяются на очереди 201. DPI в лаборатории нет, поэтому стратегии лучше контроля не находится; как стратегии работают против настоящего DPI, покажет только роутер. Сценарии службы проверяются и по отдельности на штатном BusyBox под qemu: `tools/lab/test-update.sh` (обновление из релизов), `test-watch.sh` (сторож туннеля), `test-failover.sh` (запасной сервер), `test-sub.sh` (подписка), а также `test-lists.sh` и `test-zapret-test.sh`.

## Очерёдность приёмки на устройстве

1. Снять профиль BE7000 в режиме чтения (`tools/device/preflight.sh`): ядро, модули, свободное место, мосты и порты Wi-Fi, сборка dnsmasq, метки firewall.
2. Установить пакет, проверить автозапуск после перезагрузки с WAN и без него, сохранность `firewall.mitt` после перезагрузки.
3. Проверить правило «устройство → домен → TrustTunnel»: у клиента меняется внешний адрес для домена, остальные сайты и соседнее устройство идут напрямую, штатная панель Xiaomi доступна.
4. Проверить простую панель с нуля (ссылка на сервер, сервисы, выбранные устройства, «Весь интернет» у устройства), переключение на запасной сервер и возврат, обновление из панели, IPv6 через VPN с сервером, где есть IPv6, Zapret по кабелю и Wi-Fi, подбор стратегии против DPI провайдера, обновление списков с GitHub, защищённый DNS и DNS через VPN, блокировку рекламы, поведение при остановке клиента и при включённом аппаратном ускорении.
5. Измерить расход RAM, время холодного старта и пропускную способность туннеля на процессоре роутера.
